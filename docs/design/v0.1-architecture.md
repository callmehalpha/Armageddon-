# Armageddon v0.1 — Revised Technical Design

Status: **Direction approved. Product decisions locked (§13). Phase 0 prototypes P1, P2, P4 and P5 complete; their design changes P-1…P-14 are incorporated (§14). Implementation in progress.**

This document is the contract for v0.1. Implementation follows it. A change to it is made in a reviewed PR to this file before (or together with) the code that depends on it. Prototype results update §11, and where they invalidate an assumption, they propose a design change here rather than silently diverging.
Supersedes: sections 3, 4, 10–17, 34, 37, 42–44, 56, 59 of the original Technical Product Plan.
Everything not mentioned here (runtime providers, Docker, networking, snapshots, plugin SDK, commercial layer) keeps its original intent, re-anchored on the model below.

---

## 0. Decisions this revision implements

| # | Decision | Consequence in this design |
|---|----------|----------------------------|
| D1 | `.git` is never synchronized file-by-file | Committed history moves only via the Git protocol to a server-hosted canonical repository (§5). Uncommitted state moves via a separate checkpoint protocol (§6). |
| D2 | The server is the workspace authority | Lease + epoch fencing + compare-and-swap commits, all decided by the server (§4). |
| D3 | Server-first remote development is the primary v0.1 workflow | The default writer is the **server seat** (browser IDE, terminal, SSH). Local copies are **replicas**: read-only followers by default, writers only while holding the lease (§3, §4). |
| D4 | The sync layer is abstracted | `TreeSync` interface owns capture/transport/apply only; authority, ordering and conflict policy live in the core (§6.8). Syncthing is one candidate implementation evaluated in prototype P7 (§11). |
| D5 | SQLite by default, PostgreSQL later | Repository interfaces, portable SQL, authority decisions expressed as conditional updates (§8). |
| D6 | No mandatory OAuth app | Built-in accounts, device pairing via a device-code flow, device keys. Git-provider integrations are optional credentials (§7). |

## 1. Invariants

Everything below exists to keep these true. Tests (§11, §12) are written against them.

- **I1 — Single writer.** Each workspace has exactly one writer seat at a time (the *lease holder*). Every write carries the lease *epoch*; writes with a stale epoch are rejected (fencing).
- **I2 — Server truth.** The server's committed state — the database, the canonical Git repository, and the current checkpoint — is the workspace. Device state is either a replica of it or a proposal to it.
- **I3 — No acknowledged loss.** Once the server acknowledges a checkpoint or a ref update, it is never lost by any Armageddon operation.
- **I4 — Quarantine before overwrite.** Armageddon never overwrites or discards local state that has not reached the server. It first uploads it to an append-only quarantine area.
- **I5 — Git moves through Git.** History (objects and refs) moves only through `git fetch` and `git push`. Armageddon never copies files inside `.git`.
- **I6 — Server ordering.** Order is defined by server-assigned `(epoch, seq)`, never by wall clocks.
- **I7 — Verified apply.** A replica applies `from → to` only after verifying that it currently equals `from`.
- **I8 — No executable state flows up.** Git hooks, Git config other than an allowlist, and Armageddon agent config never flow from a device to the server.

### 2.2 Seats

A **seat** is a place where the workspace can be written:

- **Server seat** (default lease holder). The server worktree `tree/` is attached to the canonical repo. Browser IDE (code-server), browser terminals, `armageddon shell`, and the optional SSH endpoint all operate here. Several sessions on the server seat are one writer, the same as two editors open on one laptop.
- **Device seat.** A paired device's local replica. It is a writer only while it holds the lease.

### 2.3 Access paths in v0.1

| Path | Seat | Needs agent? |
|------|------|--------------|
| Browser IDE (code-server) | server | no |
| Browser terminal | server | no |
| `armageddon shell <ws>` (PTY over WebSocket) | server | CLI only |
| SSH endpoint for VS Code Remote-SSH and JetBrains Gateway (stretch, P8) | server | CLI only (writes the SSH config) |
| Local replica, follow mode | none (read-only mirror) | yes |
| Local replica, write mode (`armageddon work local`) | device | yes |

A borrowed laptop with only a browser is a fully supported path. The agent is required only for local replicas.

### 2.5 Privilege boundary

There are three trust levels. Each boundary is enforced by the operating system, not by convention.

| Principal | Runs | Trusted with |
|-----------|------|--------------|
| `root`: `armageddon-helper` | the privileged helper only | the allowlisted operations below, nothing else |
| `armageddon` (system user) | server, API, authority, Git HTTP front end | DB, keys, `checkpoints.git`, journals |
| `ws-<id>` (one per workspace) | everything that runs *in* a workspace: shells, code-server, SSH sessions, dev servers, **all Git commands on `repo.git` and `tree/`** | that workspace's `repo.git`, `tree/`, `home/` |

**The helper is not a general execution mechanism.** It accepts typed requests from one unix socket. That socket is reachable only by the `armageddon` uid, checked with `SO_PEERCRED` and socket file mode 0600. The helper has no request type that runs a caller-supplied command as root. The complete v0.1 API:

| Operation | Parameters (all validated) | Notes |
|-----------|----------------------------|-------|
| `CreateWorkspaceUser` | workspace ID | creates `ws-<id>` with no login shell, no password, no sudo, no supplementary groups |
| `DeleteWorkspaceUser` | workspace ID | only users matching `ws-[a-z0-9]{8,}` |
| `PrepareWorkspaceDirs` | workspace ID | creates and chowns `repo.git`, `tree/`, `home/` under `/var/lib/armageddon/workspaces/<id>/` only, resolving paths with `openat2(RESOLVE_NO_SYMLINKS \| RESOLVE_BENEATH)` |
| `SpawnInWorkspace` | workspace ID, process kind ∈ {`pty-shell`, `code-server`, `ssh-session`, `git-service`, `runtime-command`}, argv, env allowlist, PTY fd | runs **as `ws-<id>`** in that workspace's cgroup, with `NoNewPrivileges` and the workspace dir as cwd. argv is not interpreted with root privilege, so it cannot elevate. Returns a handle. |
| `SignalWorkspace` | workspace ID, handle or "all", signal | can only signal processes in that workspace's cgroup |
| `SetWorkspaceLimits` | workspace ID, CPU/memory/pids | cgroup v2 limits |
| `ComposeUp` / `ComposeDown` / `ComposePs` (later phase) | workspace ID, project path | the helper parses the Compose file and **rejects** `privileged`, `cap_add`, host `network_mode`/`pid`/`ipc`, `devices`, bind mounts outside the workspace dir, and any mount of the Docker socket. Workspaces never get the Docker socket. |
| `ConfigurePortProxy` (later phase) | workspace ID, container or loopback port | controlled network configuration only |

**Git commands run as the workspace user.** `repo.git` is necessarily writable by `ws-<id>`, because `git commit` in `tree/` writes there. So a workspace process can edit `repo.git/config` and plant command-executing settings: `core.hooksPath`, `core.fsmonitor`, filter drivers, `core.sshCommand`, `diff.external`. Therefore:

- The server **never** runs Git as `armageddon` against `repo.git` or `tree/`. Every such invocation goes through `SpawnInWorkspace(kind=git-service)` and runs as `ws-<id>`: `upload-pack`/`receive-pack` for the HTTP endpoint, apply, `fsck`, and seat checkpoint capture of `tree/`. A malicious workspace can then only hurt itself.
- The HTTP front end (auth, epoch check, the fencing lock) runs as `armageddon`. Only the Git protocol process runs as `ws-<id>`.
- Server-owned hooks (trash refs, epoch re-check) are passed with `-c core.hooksPath=…` on the command line. They talk to the authority over a separate per-workspace socket that accepts only that workspace's requests. They are a convenience, not the security boundary; the fencing lock (§4.2) is.
- `checkpoints.git` is owned by `armageddon` and never opened by workspace processes. Data moves between the two repos through the Git protocol (a `git-service` process pushes to an `armageddon`-side receiver), never through shared object directories.

The prototype that validates this is P6, rescoped in §11.

## 3. State machines

The observable state of a workspace is the combination of three machines:

- **Lifecycle**, owned by the server. Gates which operations are allowed.
- **Lease**, owned by the server. Decides who may write.
- **Replica**, one per device. Owned by the agent and mirrored to the server for display.

### 3.1 Workspace lifecycle

```
            create
   ∅ ─────────────────▶ CREATING ──▶ IMPORTING ──ok──▶ READY ◀──────────────┐
                                        │ fail                │  ▲          │
                                        ▼                     │  │ repaired │ restored
                                     FAILED                   │  │          │
                                        │ delete      integrity│  │          │
                                        ▼             / disk   ▼  │          │
                                    DELETING ◀────────────── DEGRADED ──▶ RESTORING
                                        │                     ▲    (from snapshot/backup)
                                        ▼                     │
                                    DELETED (tombstone)   READY ──archive──▶ ARCHIVED ──unarchive──▶ READY
```

| State | Reads | Writes (commits, ref updates) | Seat sessions | Entered when |
|-------|-------|-------------------------------|---------------|--------------|
| CREATING | – | – | – | row inserted, directories being created |
| IMPORTING | – | – | – | source being imported: empty init, clone from URL, or seed upload from a device |
| READY | ✓ | ✓ | ✓ | import done, or repair/restore succeeded |
| DEGRADED | ✓ | ✗ (rejected with a reason) | read-only | `git fsck` failure, disk-full, journal replay failure, checkpoint/ref mismatch |
| RESTORING | – | – | – | restore from snapshot or backup in progress |
| ARCHIVED | metadata only | ✗ | ✗ | user archives; runtimes stopped, data kept |
| FAILED | – | – | – | import failed; can be retried or deleted |
| DELETING / DELETED | – | – | – | delete requested; tombstone kept for audit |

Runtimes and services have their own per-service state (later phases). They are not lifecycle states.

### 3.2 Lease

```
                    acquire(R) [holder online]                       flush+release ok
     HELD(h, e) ─────────────────────────────▶ HANDOFF(h → R, e) ─────────────────────▶ HELD(R, e+1)
        │  ▲                                        │
        │  │ heartbeat resumes                      │ holder unresponsive > T_handoff
        │  │                                        ▼
        └──┴── heartbeat lost > T_stale ──────▶ STALE(h, e) ──force_takeover(R)──▶ HELD(R, e+1)
```

- `h` and `R` are seats: `server` or `device:<id>`. The initial state is `HELD(server, 1)`.
- The epoch increments on **every** change of holder, including forced takeover. It never decreases.
- STALE is informational: a sleeping laptop is STALE and still the holder. Nothing transfers automatically. A takeover is always an explicit user action, either one click in the UI or `armageddon work remote --force`.
- Revoking a device that holds the lease is an immediate forced takeover by the server seat.
- Defaults: `T_stale` = 2 min without heartbeat; `T_handoff` = 30 s for the holder to flush.

### 3.3 Replica (per device, per workspace)

```
 NEW ─▶ CLONING ─▶ FOLLOWING ◀──────────── apply ok ─── APPLYING ◀─ checkpoint.committed
                     │   ▲                                   │ base mismatch
     local edit      │   │ quarantine done                   ▼
     detected        ▼   │                              QUARANTINING
                   DIRTY ┴──(a new checkpoint arrives)──▶ QUARANTINING
                     │
                     │ user runs `armageddon work local` (explicit; never automatic)
                     ▼
                  ACQUIRING ─ok─▶ WRITING ─release─▶ RELEASING ─▶ FOLLOWING
                     │
                     │ server moved since last apply → local edits quarantined, then WRITING from current
                                     │
                                     │ commit rejected: lease_lost
                                     ▼
                                QUARANTINING ─▶ FOLLOWING

 Orthogonal flags: OFFLINE (no server connection; inner state frozen) and ERROR (needs `armageddon doctor`).
```

Key rules:

- **CLONING** is clone plus **seed** (P-2). A fresh `git clone` is not byte-identical to the writer's tree when attributes normalise line endings or filters run on checkout. So the new replica captures its own tree and applies the diff to the current checkpoint; it never assumes the clone equals the checkpoint.
- **FOLLOWING** replicas receive every committed checkpoint and apply it with I7 verification.
- **DIRTY** means the user edited a replica without the lease. The agent **never takes the lease on its own** (decision Q2). It notifies the user: "You edited a read-only replica. The workspace is owned by Server. Run `armageddon work local` to take ownership." The local edits stay on disk until one of two things happens:
  - The user takes ownership explicitly. If the server has not moved since the replica's last applied checkpoint, the edits are a fast-forward and become the first checkpoint of the new epoch. Otherwise they are quarantined first, and the replica starts writing from the server's current state.
  - A new checkpoint arrives from the server. The local edits are quarantined (I4) and the server state is applied.
- **WRITING** replicas capture and commit checkpoints continuously.

## 4. Authority and locking model

### 4.1 Authority actor

Each workspace has one in-process **authority actor**: a goroutine that owns a command queue. Every state-changing operation for a workspace goes through it, which serializes them:

`AcquireLease`, `ReleaseLease`, `ForceTakeover`, `Heartbeat`, `CommitCheckpoint`, `AuthorizeRefUpdate`, `Quarantine`, lifecycle transitions.

Each command runs inside a single SQLite `BEGIN IMMEDIATE` transaction. All authority decisions are also written as **conditional updates**, so they would stay correct with several server processes on PostgreSQL later:

```sql
-- lease transfer (fencing)
UPDATE leases SET holder_kind=?, holder_device_id=?, epoch=epoch+1, state='held', acquired_at=?, heartbeat_at=?
 WHERE workspace_id=? AND epoch=?;                 -- 0 rows ⇒ someone else won; return conflict

-- checkpoint commit (compare-and-swap on the current pointer)
UPDATE workspaces SET current_checkpoint_id=?, checkpoint_seq=checkpoint_seq+1, row_version=row_version+1
 WHERE id=? AND current_checkpoint_id IS ? AND state='ready';
```

### 4.2 What the lease guards

| Operation | Requires |
|-----------|----------|
| Push to `repo.git` (`refs/heads/*`, `refs/tags/*`) | caller is the holder and the request carries the current epoch |
| Commit a checkpoint | holder + current epoch + `parent == current` (CAS) |
| Server seat interactive write sessions (IDE, terminal input, SSH) | server is the holder |
| Fetch `repo.git` / checkpoints | any non-revoked device of a workspace member |
| Push to `checkpoints.git` `refs/staging/<own-device>/*` | non-revoked device (the commit step checks the epoch) |
| Push to `checkpoints.git` `refs/quarantine/<own-device>/*` | non-revoked device, **any epoch** (append-only, quota-limited) |

The epoch travels in the `X-Armageddon-Epoch` header on API calls and Git HTTP requests. The agent configures `http.extraHeader` per invocation, so the header is never written to `.git/config`.

**Fencing lock for Git pushes.** An epoch check at the start of a push is not enough, because the lease could change while `receive-pack` is still running. So the HTTP front end does the following for each `git-receive-pack` request:

1. Take the workspace's *fence* as a reader, a per-workspace read/write lock.
2. Check the lease holder and epoch.
3. Run `receive-pack` to completion.
4. Release the fence.

Every lease transition (handoff, release, forced takeover, revocation) takes the fence as a writer, so it waits for in-flight pushes to finish. Pushes have a time limit (default 10 min) so a stuck push cannot block a takeover indefinitely. When the limit is hit, the push process is killed, and Git's ref-update atomicity means no partial update lands.

### 4.3 Server seat while a device holds the lease

When the lease moves to a device:

1. Interactive server sessions for the workspace are closed. code-server stops, PTYs get SIGHUP after a banner warning, and SSH sessions close.
2. Server development processes for the workspace stop: runtimes, dev servers, watchers and the workspace's other process groups. Persistent Docker services (databases, Redis) keep running, because they do not write to the working tree. There is no per-workspace override in v0.1 (decision Q1). This prevents server processes from editing tracked files, and it means only one environment ever believes it is authoritative. When the lease returns to the server, the user restarts them, or `armageddon work remote --restart` does it.
3. The server worktree becomes a **follower**. It applies each committed checkpoint like any replica, so a forced takeover resumes from the latest state.
4. If tracked files on the server change while the lease is elsewhere (server drift), the change is detected at the next apply. It is quarantined as `quarantine/server/...` and reported, never merged silently.

### 4.4 Handoff protocol (graceful)

```
 Requester R            Authority                         Holder H
     │ AcquireLease(R)      │                                  │
     │─────────────────────▶│ lease: HELD(H,e) → HANDOFF(H→R,e)│
     │                      │── flush_and_release(e) ─────────▶│ (WS event; server seat handled in-process)
     │                      │                                  │ block if git op in progress (§5.6) → error to R
     │                      │                                  │ wait for quiescence (≤ 5 s)
     │                      │◀─ push refs (epoch e) ───────────│
     │                      │◀─ CommitCheckpoint(e, parent=C) ─│ → current = C'
     │                      │◀─ Release(e) ────────────────────│
     │                      │ lease: HELD(R, e+1)              │ replica → FOLLOWING
     │◀── granted(e+1, C') ─│
     │ fetch refs + C', apply (I7). Local edits made on top of C' are kept (fast-forward);
     │ edits made on top of an older checkpoint are quarantined first (I4).
```

If `H` does not complete within `T_handoff`, the request fails with `holder_unresponsive`. The UI offers forced takeover and shows the age of the last checkpoint.

### 4.4a Lease state in every resync and heartbeat (P-7, P-9)

Every resync reply (`GET …/current`) and every heartbeat reply carries `(holder, epoch, current checkpoint)`. Two rules depend on this:

- **Missed grant.** If the reply names this device as holder at an epoch newer than the one it knows, the device processes the reply exactly as a grant. This covers a lost `granted` message, or a crash before processing it. Without this rule, the authority thinks the device writes and the device thinks it follows: the workspace stalls (found by P4).
- **Writer resync.** A writer that holds the current epoch, has nothing pending, and sees current ahead of its base adopts current. Its own late-landing commit got there first. Any local edits made on the stale base are quarantined before adopting.

### 4.5 Forced takeover

```
 Authority: lease HELD/STALE(H, e) → HELD(R, e+1). Audit event `lease.forced` records the last checkpoint seq and its age.
 Later, H reconnects and tries any write with epoch e → 409 lease_lost.
 H's agent: capture the local state → push to refs/quarantine/<H>/<ts> → POST /quarantines → re-clone or apply current → FOLLOWING.
 The user sees: "MacBook's changes after 14:02:11 were kept in quarantine Q-7. `armageddon quarantine diff Q-7`".
```

The data at risk in a forced takeover is whatever the old holder wrote after its last acknowledged checkpoint. It is not lost; it reaches quarantine when the device returns. It is unavailable only if the device never returns. That window is the **RPO**: the time between checkpoints, default 2 s after quiescence and at most 15 s while edits continue.

### 4.6 Why not finer-grained locks

Per-file or per-branch locks would bring back concurrent writers and the merge problems D3 rules out. One lease per workspace is coarse, simple and easy to verify. Teams that need concurrent writers use separate workspaces and Git branches, which is how Git expects it.

## 5. Git synchronization protocol

### 5.1 Repositories

| Repo | Location | Holds | Visible to user |
|------|----------|-------|-----------------|
| `repo.git` | server | `refs/heads/*`, `refs/tags/*`, `refs/notes/*`, `HEAD` (default branch); served by a **native smart-HTTP handler** that spawns `upload-pack`/`receive-pack --stateless-rpc` (P-6) | yes: it is "the repo" |
| server worktree `tree/` | server | `git worktree` of `repo.git` | yes |
| user clone | device | normal clone with remote `armageddon` → `https://<server>/git/<ws>/repo.git` | yes |
| `checkpoints.git` | server | `refs/checkpoints/<seq>`, `refs/staging/*`, `refs/quarantine/*`, `refs/trash/*` | no |
| `shadow.git` | device | local checkpoint captures and an unsent checkpoint queue | no |

`checkpoints.git` and `shadow.git` are separate from the user's repository so that:
- `git log --all` and `git branch -a` stay clean;
- a user running `git gc --prune=now` can never break checkpoints, because there are no alternates between them. Storage is duplicated in v0.1; deduplication is a later optimization.

### 5.2 Server repository configuration

```
core.logAllRefUpdates = always       # reflogs in the bare repo
receive.denyCurrentBranch = ignore   # verified: required to push to a branch checked out in tree/
receive.denyDeletes = false
receive.fsckObjects = true
gc.auto = 0                          # Armageddon schedules gc itself
gc.reflogExpire = 90.days
core.hooksPath = /usr/lib/armageddon/hooks   # server-owned hooks only (I8)
```

### 5.3 Pushing history (writer = device)

The agent watches `.git/HEAD`, `.git/refs/**`, `.git/packed-refs` and `.git/logs/HEAD`. It also rescans every 30 s. When refs change, it runs:

```
git -c http.extraHeader="X-Armageddon-Epoch: <e>" \
    push --atomic --porcelain --prune armageddon \
    '+refs/heads/*:refs/heads/*' '+refs/tags/*:refs/tags/*'
```

- The write is a **mirror**: the holder is authoritative, so force updates and deletions are allowed.
- **Nothing is lost on the server.** The `pre-receive` hook calls the authority over a unix socket, passing device identity from the HTTP layer in the environment. The authority checks the epoch (I1). For every deletion and every non-fast-forward update, it records the old OID under `checkpoints.git:refs/trash/<ts>/<ref>` (fetched locally). This matters because branch deletion also deletes the reflog. `armageddon git trash` lists and restores these.
- `--atomic` makes a multi-ref update all-or-nothing.
- The agent never touches the user's `origin` or other remotes.

### 5.4 Pushing history (writer = server seat)

The server worktree shares the object store and refs of `repo.git`. A commit made in a browser terminal is already canonical. A `reference-transaction` hook on `repo.git` (Git ≥ 2.28) emits `refs.updated` events and runs the same trash recording for local deletions and forced updates. This is checked in prototype P5.

**Best effort for local server-seat Git (P-13).** The `reference-transaction` hook for local Git is configured through `repo.git/config`, which the workspace user can edit. So a workspace can disable its own trash recording for local operations. That is self-harm only. Device pushes are always protected, because the HTTP path injects `core.hooksPath` through server-owned `GIT_CONFIG_*`. Interactive shells spawned by the helper also get `core.hooksPath` through the environment, which covers the common case.

### 5.5 Followers receiving history

When `refs.updated` arrives, a follower's agent runs:

```
git fetch --prune --update-head-ok armageddon '+refs/heads/*:refs/heads/*' '+refs/tags/*:refs/tags/*'
```

Before fetching, the agent compares local `refs/heads/*` with what it last recorded from the server. If a branch differs (the user committed locally without the lease), it pushes those refs to `refs/quarantine/<device>/<ts>/heads/<b>` first (I4), then overwrites. The checked-out branch's working tree is not touched by fetch. It changes only when a checkpoint is applied (§6.5), and the checkpoint names the HEAD it expects.

### 5.6 Git operations in progress

These are detected through: `index.lock`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge/`, `rebase-apply/`, `BISECT_LOG` and `sequencer/`.

| Situation | Behaviour |
|-----------|-----------|
| `index.lock` present | Skip capture and ref push. Retry with backoff. Stale lock older than 10 min → `doctor` warning. |
| Merge, rebase, cherry-pick, revert or bisect in progress | Checkpoints are still captured. The working tree and index (including conflict stages 1–3) are recorded, plus `op_in_progress`. **Graceful handoff is refused** until the operation finishes or is aborted. |
| Forced takeover while the old holder was mid-operation | The new holder gets the working tree and the conflicted index. Sequencer state is not transferred. The UI shows "rebase in progress on MacBook was not transferred; ORIG_HEAD = <oid>". |

### 5.7 What is and isn't synchronized from `.git`

| Item | v0.1 |
|------|------|
| Objects, branches, tags, notes | ✓ via Git protocol |
| `HEAD` (checked-out branch or detached OID) | ✓ via checkpoint metadata |
| Index (staged state, including conflict stages) | ✓ via checkpoint index manifest |
| Stash | ✓ best-effort: each `stash@{n}` commit travels with the checkpoint (pushed under the writer's `refs/staging/<device>/…` namespace and listed in `meta.stashes`) and is restored in order on apply |
| Remotes (`remote.*.url`, `remote.*.fetch`) and `branch.*.{remote,merge}` | ✓ allowlisted config, server-stored, written into replicas |
| Remote-tracking refs (`refs/remotes/origin/*`) | ✗ each seat runs `git fetch origin` itself |
| Hooks, other `.git/config`, `info/exclude`, `rerere` cache | ✗ (I8) |
| Sequencer and rebase state | ✗ (handoff is blocked instead) |
| LFS objects, submodule working trees | ✗ unsupported in v0.1 (§11) |

### 5.8 External providers (GitHub, GitLab, etc.)

`origin` is ordinary Git configuration. Pushing to GitHub happens from whichever seat runs `git push origin`:
- **Server seat:** uses an optional server-side credential, either a stored PAT or a deploy SSH key generated by the server (§7.5).
- **Device seat:** uses the user's own local credentials.

Armageddon never needs a provider account to work.

## 6. Working-tree synchronization protocol

### 6.1 Concepts

- **Working state**: `(HEAD, index, working files)` of a seat. Working files are filtered by the sync policy (§6.6).
- **Checkpoint**: an immutable, content-addressed capture of a working state, plus metadata.
- **Current**: the server's pointer to the latest committed checkpoint. It is the authoritative working state (I2).

### 6.2 Checkpoint format (v0.1 implementation: git-shadow)

A checkpoint is a commit object in `checkpoints.git` (or `shadow.git` before upload) whose tree is:

```
/worktree      tree    working files after policy filtering; modes 100644 / 100755 / 120000 (symlink)
/staged        tree    (only if non-empty) blobs staged in the index that differ from /worktree,
                       named by their oid, so the checkpoint is self-contained and transfer carries them
/meta.json     blob    {
                         "format": 1,
                         "workspace_id": "...", "epoch": 7, "seq": 1042,          // seq assigned on commit
                         "parent": "<checkpoint oid | null>",
                         "device_id": "... | server",
                         "head": {"ref": "refs/heads/main" | null, "oid": "<commit oid>"},
                         "op_in_progress": null | "merge" | "rebase" | ...,
                         "empty_dirs": ["logs/"],
                         "stashes": ["<commit oid>", ...],                         // stash@{0..n}
                         "staged": [{"mode","oid","stage","path"}, ...],          // index as delta vs HEAD (P-3)
                         "policy_hash": "sha256:...",
                         "excluded": {"oversize": ["assets/video.mov"], "count_ignored": 18234},
                         "captured_at": "2026-10-04T18:42:11Z"                    // informational only (I6)
                       }
```

- Commit parents are **not** used. The checkpoint chain lives in `meta.parent` and the database. Retention can then delete any `refs/checkpoints/<seq>` without rewriting history.
- **The index is stored as a delta against HEAD (P-3):** `git diff-index --cached HEAD` plus unmerged entries (`ls-files -u`). Its cost is O(staged changes), not O(repository): a full `ls-files -s` manifest would be ~14 MB per checkpoint at 200k files. Restore touches only the affected paths (`git reset -- <paths>` plus `update-index --index-info`), so the destination's stat cache survives.
- **Checkpoints never travel by `git fetch` or `git push` (P-1).** Fetch negotiation finds common objects only through common *commits*, and checkpoints are parentless. Measured cost: fetch resent the whole tree on every checkpoint, 100 s for a 20-file change at 200k files. Transport is a thin pack of `<checkpoint> --not <receiver's base checkpoint>^{tree}` (306 ms for the same change) over the checkpoint API (§6.4). A full pack is sent when the receiver's base has been pruned.
- Index blobs, the staged contents, are copied into the shadow repository so the checkpoint is self-contained.

### 6.3 Capture

```
GIT_DIR=<shadow.git>  GIT_WORK_TREE=<tree>  GIT_INDEX_FILE=<replica>/capture.index
  git add -A                         # respects the user's .gitignore, plus policy excludes in shadow info/exclude
  git add -f -- <preserve globs>     # e.g. .env*, see §6.6
  git rm --cached -- <oversize>      # size policy
  git write-tree                     # → worktree tree
```

- **Scoped capture (P-12).** For change sets up to ~50 paths reported by the watcher, capture runs `add -A -- <paths>` and limits `ls-files` to their directories, carrying the previous empty-directory set forward. A full capture remains the backstop: on watcher overflow, at startup, every 10 minutes, and before every lease flush. Scoped capture is enabled only once P3 shows the watcher misses nothing. Measured at 200k files with 20 changes: 896 ms p95 scoped, against 1,233 ms full. Every capture still rewrites the whole index, so at 200k+ files sub-second capture is marginal with Git as the capture engine.
- `capture.index` persists between captures. Git's stat cache makes incremental capture proportional to what changed (P1 measures this).
- `shadow.git/info/attributes` contains `* -text -eol -filter -ident -working-tree-encoding`, so bytes are captured exactly. This was checked: a CRLF file stayed CRLF despite `eol=lf` in the project's `.gitattributes`.
- Triggers:
  - watcher event, debounced: 2 s of quiet, or at most 15 s during continuous edits;
  - a ref change;
  - an explicit `armageddon sync`;
  - lease release (a flush waits for 5 s of quiet);
  - shutdown of the agent or server.
- **Checkpoints are created by capture events, never per filesystem event** (decision Q6):
  - A burst of saves (editor autosave, a formatter rewriting 300 files, `git checkout`) produces one capture after the debounce, not one per write.
  - If the captured tree, index and HEAD equal the parent's, no checkpoint is created. Saving a file without changing its content, or changing it and back, costs nothing.
  - There is a hard floor: at most one automatic checkpoint per 2 s per workspace. Explicit `armageddon sync` and lease flushes bypass the floor.
  - Expected volume is a few hundred checkpoints in an active working day, which is what the retention tiers in §13 are sized for.

### 6.4 Commit (writer → server)

```
1. Writer pushes branch refs if they changed                                     (§5.3, epoch-checked)
2. Writer uploads the checkpoint as a thin pack against its base (P-1):
      POST /v1/workspaces/{ws}/checkpoints/pack?base=<oid>   (body: pack) → staged as refs/staging/<device>/<oid>
3. POST /v1/workspaces/{ws}/checkpoints:commit
      { "epoch": e, "parent": "<oid|null>", "checkpoint": "<oid>" }
4. Authority, inside one transaction:
      a. lease.epoch == e and the holder is the caller      else 409 lease_lost {attempted_epoch: e} (P-8)
      b. current == parent                                  else 409 parent_mismatch (+ current)
      c. the checkpoint object is valid; head.oid exists in repo.git; size within quota
      d. INSERT checkpoints(seq = workspace.checkpoint_seq + 1, ...); CAS-update workspaces.current
5. After commit: update ref checkpoints.git refs/checkpoints/<seq>; delete the staging ref;
   apply to the server worktree if the server is a follower; broadcast checkpoint.committed{seq, oid}
6. 200 { "seq": 1042 }   ← the acknowledgement for I3
```

- **Idempotent.** Retrying the same `(epoch, parent, checkpoint)` after a lost response returns the original `seq`.
- **Stale rejections are ignored (P-8).** Every rejection echoes the epoch of the attempt. An agent ignores a rejection for an epoch older than its current one; its retry under the new epoch is already in flight. Honouring it would quarantine work under a perfectly valid lease (found by P4).
- **Followers download** with `GET /v1/workspaces/{ws}/checkpoints/{seq}/pack?base=<their last applied oid>`.
- **parent_mismatch for the holder** can only follow a bug or a lost acknowledgement. The writer refetches current. If current is its own earlier checkpoint, it rebases its pending queue onto it. Otherwise it quarantines its pending work.
- **Offline writer.** The writer keeps a local queue of checkpoints whose parents chain. On reconnect it commits them in order, oldest first. If the lease was force-taken meanwhile, step 4a fails and the whole queue goes to quarantine.
- **Crash between steps 4 and 5.** The database is the truth for "current". Startup reconciliation recreates missing `refs/checkpoints/*` from database rows and garbage-collects staging refs older than 24 h.

### 6.5 Apply (server → follower; also the server worktree when it is a follower)

```
apply(from, to):
  0. journal: write {from, to, phase: "verify"} (fsync)
  1. verify the local working state == from          (capture into a temp index, compare tree, index and HEAD)
       mismatch → DIRTY handling (§3.3): fast-forward/acquire, or quarantine local, then continue
  2. fetch refs (§5.5) and the `to` checkpoint objects
  3. journal phase = "files"
     for each entry of `git diff-tree -r -z --no-renames from:worktree to:worktree`:
        re-check that the on-disk file still hashes to the `from` version (cheap stat check, hash on doubt);
            changed under us → stop, quarantine, restart apply
        write to <dir>/.armageddon-tmp-<rand>, set mode, rename over the target (same filesystem, atomic);
        delete removed files; create and remove empty dirs per meta.empty_dirs
  4. journal phase = "git"
     set HEAD (symbolic-ref or detached update-ref);
     rebuild the index: `git read-tree --empty && git update-index --index-info < manifest`, then `git update-index -q --refresh`
  5. journal: done; record last_applied = to
```

**Crash recovery.** On restart, a journal entry not marked done is re-run from its phase. Each step is idempotent. A file that matches neither the `from` nor the `to` version means the user changed it during the apply. That file is quarantined.

**Apply rules found by P2 (P-4).** Resume after a crash must accept every path already in its target state:

- a delete whose path is gone, or already replaced by a directory or by its own type-change put;
- `ENOTDIR` on a path whose parent became a file, which counts as absent;
- leftover `.armageddon-tmp-*` files, which resume removes.

Parent directories of deletes are recorded *before* skipping, so pruning still happens. Git collapses a directory holding only empty directories into one entry, so capture expands it to its empty leaves.

**Displacement.** A put that finds a directory still holding only local ignored files (the writer turned a directory into a file) **displaces** that directory to a replica-private area outside the working tree, reports it, and continues. It never deletes the directory and never blocks forever.

The P2 fuzzer validated these rules over 10,000 random sequences.

### 6.6 Sync policy

Default class assignments, extending the original plan's A/B/C classes:

| Class | Default members | Mechanism |
|-------|-----------------|-----------|
| A1 History | `.git` objects and refs | Git protocol (§5) |
| A2 Working tree | tracked + untracked, non-ignored files | checkpoints |
| A3 Preserved ignored | `.env`, `.env.*` (not `.env.example`, which is tracked anyway), `.armageddon/local/**` | checkpoints (force-added) |
| B Persistent service state | Docker volumes, databases | snapshots (later phase) |
| C Derived | everything matched by `.gitignore` and not in A3, plus built-in excludes (`node_modules/`, `vendor/`, `.next/`, `dist/`, `build/`, `target/`, `__pycache__/`, `.venv/`) | not synced; rebuilt by the runtime |
| X Excluded | files > 50 MB (configurable), sockets, FIFOs, device files | reported in `meta.excluded` and `armageddon sync status` |

Overrides live in `.armageddon/sync.yaml`, which is committed with the project:

```yaml
sync:
  include_env: true            # default true (decision Q3); false removes .env* from A3
  preserve: ["config/master.key"]
  exclude:  ["tmp/**", "*.sqlite3"]
  max_file_size: 200MB
```

A per-workspace server-side setting (`armageddon workspace config <ws> sync.include_env false`) overrides the project file. This lets a user exclude secrets without committing a policy change.

**`.env` security notice (decision Q3).** `.env*` files are kept by default because they are usually needed to reproduce a development environment after a machine is lost. The notice below is shown in three places: by `armageddon workspace create`, on the first checkpoint that contains a `.env*` file (a one-time CLI and UI notice per workspace), and in the docs and `armageddon sync status`:

> `.env` files are included in workspace checkpoints by default because they are often required to reproduce a development environment. These files may contain secrets. They are stored on your Armageddon server and on devices that replicate this workspace. Set `sync.include_env: false` (or add specific exclusions) if your workspace contains sensitive credentials.

Until the secret store exists, these files are protected only by server disk permissions and the `armageddon`/`ws-<id>` boundary. Encryption at rest arrives with the secret store.

**Clarifications (P-5):**
- A directory holding only ignored files is not replicated; whatever regenerates the files regenerates the directory. Truly empty directories are replicated (`meta.empty_dirs`).
- Preserve (`.env*`) applies to **files only**. A directory matching `.env*` (commonly a Python virtualenv) stays ignored with all its contents.
- Gitlinks (submodules, nested repositories) are refused by apply with an explicit error.

The policy hash goes into every checkpoint. A policy change forces a full recapture.

### 6.7 Divergence and quarantine

A **quarantine** is a checkpoint, plus any diverged refs, pushed to `checkpoints.git:refs/quarantine/<device|server>/<ts>/...`, together with a `quarantines` row. Quarantines are append-only and are **kept until explicitly cleared** (`quarantine drop`, decision Q6). They are never removed by retention. Per-device quotas cap abuse: when a quota is reached, new quarantines from that device are refused and the user is told to clear old ones. Nothing is ever evicted silently.

```
armageddon quarantine list
armageddon quarantine diff <id>          # against current
armageddon quarantine apply <id>         # 3-way: base = quarantine's parent checkpoint; result is a normal edit by the current writer
armageddon quarantine export <id> <dir>
armageddon quarantine drop <id>
```

Armageddon never merges automatically (original plan §17). `apply` writes the 3-way result into the writer's working tree, with conflict markers where needed. The user resolves them like any merge.

### 6.8 The TreeSync abstraction

The core owns the lease, epochs, CAS, ordering, journal policy and quarantine policy. An implementation provides only capture, transport and apply:

```go
type TreeSync interface {
    // Capture the seat's working state as an immutable checkpoint (not yet committed).
    Capture(ctx context.Context, seat Seat, parent CheckpointRef, pol Policy) (Checkpoint, error)
    // Make checkpoint content available on the server (staging area). Idempotent.
    Upload(ctx context.Context, cp Checkpoint) error
    // Make checkpoint content available locally. Idempotent.
    Download(ctx context.Context, ref CheckpointRef) (Checkpoint, error)
    // Verify the seat equals `from`, then transform it to `to`. Must be crash-resumable via the journal.
    Apply(ctx context.Context, seat Seat, from, to CheckpointRef, j Journal) (ApplyResult, error) // ErrDiverged
    // Compare the seat's current state to a checkpoint (used by verify, doctor, and DIRTY detection).
    Status(ctx context.Context, seat Seat, against CheckpointRef) (TreeDiff, error)
    // Upload the seat's state to the append-only quarantine area.
    Quarantine(ctx context.Context, seat Seat, reason string) (CheckpointRef, error)
}
```

Requirements on any implementation: point-in-time capture, content addressing, idempotent transfer, and verified, resumable apply. Prototype P7 tests Syncthing against these requirements.

## 7. Authentication and identity

### 7.1 Accounts (built-in)

- Local accounts: username and password, hashed with argon2id (m=64 MiB, t=3, p=1, tunable). TOTP is optional (v0.2).
- **First admin bootstrap.** `armageddon server init` prints a one-time setup URL with a 32-byte token. It expires after 1 h and is single-use. Opening it creates the admin account. No OAuth app or email server is needed.
- Additional users are invited by an admin through a one-time link. v0.1 is designed single-admin but stores tenant-ready data.

### 7.2 Browser sessions

- Opaque session ID in an `HttpOnly; Secure; SameSite=Lax` cookie. The database stores only the SHA-256 hash.
- 12 h idle timeout, 7 d absolute.
- CSRF token on state-changing requests.
- Re-authentication is required for dangerous actions: forced takeover, device revoke, workspace delete, credential management.

### 7.3 Device identity and pairing (device-code flow, no OAuth app)

```
armageddon login https://dev.example.com
  1. The agent generates an Ed25519 keypair. The private key goes in macOS Keychain or Linux Secret Service; fallback is a 0600 file.
  2. POST /v1/pair/start {public_key, name, platform}
       → {user_code: "WDJB-MJHT", verification_url, expires_in: 600, server_cert_fingerprint}
  3. The CLI shows the code and URL. The user opens the URL in a logged-in browser (any device),
     checks the code, device name and key fingerprint, and approves. Headless alternative:
     `armageddon login --password` uses username + password (+TOTP) directly over TLS.
  4. The agent polls /v1/pair/poll → device_id
```

**Token issuance.** Nothing reusable is stored on disk:
```
POST /v1/auth/device/challenge {device_id}            → {nonce}
POST /v1/auth/device/token {device_id, nonce, sig}    → {access_token (15 min), scope}
```

Access tokens are PASETO v4.public or JWT EdDSA. They carry `sub`, `device_id`, `scope`, `exp`, and are signed by a server key with rotation. A token is re-issued by signing again; there are no refresh tokens. A lost disk exposes only the private key, and that is revocable.

**TLS trust.** With a domain, the server uses ACME (embedded certmagic). In IP-only mode it uses a self-signed certificate, and the CLI pins its fingerprint on first use, like SSH. The fingerprint is shown in the server console at `init` for out-of-band comparison.

**Git over HTTPS.** `git-credential-armageddon`, installed by the agent, returns a fresh access token on demand. Git therefore never stores a password.

**Revocation.** This is immediate for live WebSocket and SSH connections, and takes at most 15 min elsewhere. A device-level denylist is checked on every request, which makes it immediate in practice. A lease held by the revoked device is force-released (§3.2).

### 7.4 Authorization

The design is multi-user from day one, but the feature set stays simple (decision Q5). There are two fixed role sets and no configurable RBAC.

**Server roles:**
- `admin`: server settings, inviting and disabling users, read access to every workspace's metadata.
- `user`: can create workspaces and is a member of the workspaces they were added to.

**Workspace roles** (`workspace_members`):

| Action | `owner` | `member` |
|--------|:-------:|:--------:|
| Open server seat (IDE, terminal, SSH); replicate to own devices; take or hand back the lease | ✓ | ✓ |
| Read events, checkpoints, quarantines | ✓ | ✓ |
| Add or remove members (existing users only), change workspace settings, archive or delete, manage stored Git credentials | ✓ | ✗ |

```
Users        Abdul (admin), Jane (user)
Workspaces   Dokta, Armageddon
Membership   Abdul → Dokta → owner     Jane → Dokta → member     Abdul → Armageddon → owner
```

- New users join only through admin invites (§7.1).
- A workspace has at least one owner.
- Every query is scoped by `workspace_id` together with membership. A non-member gets `404`, not `403`.
- The lease is per **seat**, not per user. Two members working in the browser at the same time share the server seat, like two people at one machine. Their sessions are attributed separately in `terminal_sessions` and `events`. A device lease is held by one member's device.
- **Not built:** teams, organizations, custom roles, per-path permissions, SSO, billing.

### 7.5 Optional Git provider integrations

- **Credentials:** a stored HTTPS token (PAT) or a server-generated SSH deploy key per provider host. Encrypted at rest with a server data key (XChaCha20-Poly1305; the key is in `keys/`, mode 0600). These are exposed to server-seat sessions only through a credential helper or `SSH_AUTH_SOCK` proxy, never as files in the workspace.
- **Optional OIDC login** (GitHub, GitLab, generic OIDC): off by default. Only an admin who wants it registers an OAuth app. An external identity links to an existing local user and never replaces local accounts.

## 8. Data model

### 8.1 Persistence rules

- **Driver:** `modernc.org/sqlite`, pure Go, so the build needs no CGO and cross-compiles cleanly.
- **Settings:** WAL mode, `busy_timeout=5000`, `foreign_keys=ON`. One writer connection plus a pool of readers.
- **Portable SQL only:**
  - IDs are `TEXT` ULIDs;
  - timestamps are `INTEGER` unix milliseconds;
  - JSON is stored in `TEXT` and parsed in Go;
  - no `AUTOINCREMENT`/rowid semantics, no triggers carrying business logic, no SQLite-only upsert quirks (use `INSERT … ON CONFLICT … DO UPDATE`, which both databases support).
- `internal/store` defines repository interfaces. `store/sqlite` implements them; `store/postgres` comes later. The same contract test suite runs against every implementation.
- **Migrations:** forward-only, numbered, in `migrations/{common,sqlite,postgres}/`. Before migrating, the database is copied with `VACUUM INTO backups/pre-<version>.db`.

## 9. Installation architecture

### 9.1 Artifacts

Each release has one manifest, signed with minisign/cosign:

```
armageddon-v0.1.0/
├── manifest.json                 version, files[], sha256, min_upgrade_from, schema_version
├── armageddon-linux-{amd64,arm64}
├── armageddon-darwin-{amd64,arm64}
├── code-server-<pinned>-linux-{amd64,arm64}.tar.gz   (optional component)
└── hooks/                        server Git hooks (thin shims that call the unix socket)
```

One binary contains the server, privileged helper, agent and CLI as subcommands. Runtime dependencies on the server:
- **Required:** `git` ≥ 2.40.
- **Optional:** Docker Engine (for later phases).

There is no PostgreSQL and no external reverse proxy; TLS is embedded.

### 9.2 Server install

`curl -fsSL https://install.armageddon.dev | sh` then `armageddon server init`. The installer:

1. detects the OS (Debian/Ubuntu, Fedora/RHEL, Alpine later) and the architecture;
2. checks requirements: kernel, ≥1 GB RAM, ≥10 GB disk, ports 80/443 (or a custom port);
3. installs `git` through the package manager if it is missing;
4. downloads the manifest and verifies its signature, then downloads and verifies the artifacts. With `--bundle file.tar` it uses a local bundle, so it runs offline (designed now, shipped later);
5. lays out files:
   ```
   /opt/armageddon/versions/<v>/      immutable per version
   /opt/armageddon/current → versions/<v>
   /usr/local/bin/armageddon → /opt/armageddon/current/armageddon
   /etc/armageddon/server.yaml
   /var/lib/armageddon/               (§2.4)
   ```
6. creates the `armageddon` system user (server, unprivileged). Per-workspace users `ws-<id>` are created later by the helper when each workspace is created (§2.5). None of them can read `/var/lib/armageddon/{armageddon.db,keys}` or any other workspace;
7. installs systemd units:
   - `armageddon-helper.service`, which runs as root and serves only the allowlisted API of §2.5 on a 0600 socket owned by `armageddon`. It has `CapabilityBoundingSet` limited to what that API needs (`CAP_SETUID`, `CAP_SETGID`, `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_KILL`, `CAP_SYS_ADMIN` for cgroups) and no network access;
   - `armageddon.service` (`User=armageddon`, `NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/armageddon`);
8. starts the services.

`armageddon server init` then:
- asks for a domain + ACME email, or chooses IP-only mode;
- generates the server keys;
- prints the setup URL and the certificate fingerprint.

The Docker Compose deployment ships the same binary in one image with `git` (and optionally code-server), with `/var/lib/armageddon` on a volume. In the container, the helper and server run in the same container under different users. Per-workspace users are created inside the container. Docker-in-Docker is not supported; Compose operations use the host Docker socket, which is visible **only to the helper**.

### 9.3 Lifecycle commands

| Command | Behaviour |
|---------|-----------|
| `armageddon server status` | services, version, schema version, disk, workspace states, lease summary |
| `armageddon server update [--to v]` | download + verify → `VACUUM INTO` DB backup → stop → switch `current` → migrate → start → health check (60 s). On failure: switch back and restore the pre-migration DB. |
| `armageddon server rollback` | the previous version + matching DB backup |
| `armageddon server backup [--to dir]` | consistent backup: DB via `VACUUM INTO`; per workspace, the authority is quiesced briefly (commits paused), then `git bundle --all` of `repo.git` and `checkpoints.git` refs. Config and (optionally, encrypted) keys are included. |
| `armageddon server restore <backup>` | onto a fresh install; workspaces come back in READY with the lease held by the server |
| `armageddon doctor` | §10 checks + `fsck` + DB/ref reconciliation report |
| `armageddon server uninstall [--purge]` | removes services and binaries; `--purge` also removes data after typed confirmation |

Configuration files are never hand-edited during upgrades. Config has a `version` key and is migrated by the binary.

### 9.4 Client install

- **macOS:** `brew install armageddon`, or the curl script.
- **Linux:** the curl script, or `.deb`/`.rpm` later.

The agent is registered as a user-level service (launchd LaunchAgent or a `systemd --user` unit). `armageddon login <url>` pairs the device (§7.3). `armageddon workspace clone <ws>` creates a follower replica.

## 10. Failure and recovery scenarios

The RPO ("data at risk") is measured against I3: acknowledged data is never at risk.

| # | Scenario | Detection | Behaviour | Data at risk | Recovery |
|---|----------|-----------|-----------|--------------|----------|
| F1 | **Laptop dies, server-first workflow (default)** | — | Nothing changes; the laptop never held the lease. | none | Log in on any machine or browser and continue. North-star case, ≪10 min. |
| F2 | **Laptop dies while holding the lease** (local write mode) | heartbeat lost → STALE | The UI shows "MacBook holds the workspace, last checkpoint 6 s ago" and offers takeover. | edits after the last ack (≤ ~15 s) | Forced takeover → new seat continues from current. If the laptop is recovered later, its tail goes to quarantine. |
| F3 | Laptop offline with the lease, keeps working | WS down | Checkpoints queue locally (`shadow.git`). | until reconnect | On reconnect: commit the queue in order. If the lease was taken meanwhile: the queue goes to quarantine. |
| F4 | Follower edited offline without the lease | DIRTY on reconnect | The user is prompted to take ownership explicitly; nothing is automatic. If the server has not moved and they run `work local`: fast-forward. If a new checkpoint arrives first: quarantine. | none | `quarantine apply` if wanted. |
| F5 | Network drops mid-upload or mid-commit | HTTP error or timeout | Retry with the same `(epoch, parent, oid)`; idempotent. | none | Automatic. |
| F6 | Server process crashes mid-commit | startup reconcile | DB is truth; refs are rebuilt; staging refs garbage-collected; apply journals replayed. | none for acked data | Automatic. Unacked checkpoints are retried by writers. |
| F7 | Server crashes mid-apply on its worktree | journal not done | Resume from the journal phase. Files matching neither version go to server-drift quarantine. | none | Automatic. |
| F8 | Server disk full | write errors / free-space monitor (<5%) | Workspaces → DEGRADED: commits rejected with `disk_full`; writers keep queuing locally; interactive sessions get a banner. | none | Free space → `doctor --repair` → READY. |
| F9 | **Server lost entirely** (VPS deleted) | devices can't connect | Replicas keep working read-only; a writing device keeps queuing. | server-only state not on any replica (other workspaces, snapshots) unless backed up | **(a)** `server restore <backup>` on a new VPS, or **(b)** new server + `armageddon workspace seed --from-replica`, which pushes the replica's full refs and latest checkpoint as a new workspace. (b) makes every follower a disaster-recovery copy; this is why follower replicas matter even in server-first mode. |
| F10 | Corruption in `repo.git` | `fsck` on schedule or doctor | DEGRADED. | possibly objects | Restore objects from a replica (`git fetch` from the device into the server via `workspace repair --from-device`), or from the latest backup bundle. |
| F11 | Git op in progress during handoff | §5.6 | Handoff refused with an explanation. | none | Finish/abort, then retry, or force takeover (sequencer state not transferred). |
| F12 | Stolen device | user report | Revoke → tokens dead, live connections closed, lease force-released, its quarantine uploads refused. | the device's local copy (outside Armageddon's control) | Rotate any Git-provider credentials that lived on the device. |
| F13 | User runs `git gc --prune=now` / `git reflog expire` on the server seat | — | `repo.git` loses unreachable objects, as Git normally would. Checkpoints and trash are unaffected (separate repo, no alternates). | none from Armageddon's perspective | `armageddon git trash` restores deleted or forced refs. |
| F14 | Server-side process edits tracked files while a device holds the lease | apply verify mismatch | Server drift → quarantine (`source=server`), then apply. | none | Report + `quarantine diff`. |
| F15 | Clock skew between machines | — | Irrelevant to ordering (I6). Token `exp` has ±2 min leeway; large skew → doctor warning. | none | — |
| F16 | Upgrade fails (migration or startup) | health check | Automatic rollback of binary + DB. | none | Inspect logs; retry. |
| F17 | Very large or excluded file changed | capture policy | Not synced; listed in `sync status` and checkpoint meta. | that file | Raise `max_file_size` or add to `preserve`; Git LFS later. |
| F18 | Both server seat and a (non-holder) device edit at once | DIRTY on device | Device edits quarantined (server moved). | none | `quarantine apply`. This is the "no concurrent writer by default" rule. |

## 11. Remaining risky assumptions and prototypes

**Phase 0 results (2026-10-04):** P1 pass, but marginal at 200k files. P2, P4 and P5 pass. Details are in [`prototypes/README.md`](prototypes/README.md) (on the prototypes branch), and the resulting changes are in §14.

The P1 storage criterion is replaced (P-11) by: ≤ 20 KiB per checkpoint after gc, and scheduled `gc` at least daily, off the commit path. Measured: 11.8 KiB per checkpoint. The original ratio-to-edit-bytes criterion measured the wrong thing: per-checkpoint tree rewrites dominate the cost.

P3, P6, P7, P8 and P9 remain open. P6 gates M3 of the implementation plan.


Each prototype is timeboxed, throwaway, lives in `prototypes/Pn-*`, and ends with a one-page result in `docs/design/prototypes/`.

**Known unsupported in v0.1, documented rather than prototyped:**
- Git LFS objects. Pointer files sync; LFS content is fetched per seat from the LFS server.
- Submodules and nested `.git` directories. `git add` records them as gitlinks, so their working-tree changes are not captured. Doctor warns.
- Windows.
- Concurrent writers.
- Repositories larger than about 5 GB, pending P1/P5 data.

**Lower risk, quick checks inside other prototypes:** SQLite contention under WS event load (P4 harness); embedded ACME and IP-only fingerprint pinning (P5 server); editors reloading files changed by atomic rename (P2).

Server-first ordering means a usable product exists before the agent does.

| 2 — Follower replicas | 6–7 | agent, device pairing, device tokens, credential helper, `workspace clone`, follow mode (refs + checkpoint apply + journal), `sync status`, `workspace seed --from-replica` | F9(b): delete the server, seed a new one from a laptop replica, continue |

Snapshots with database-aware volume backups (original Phase 4) and networking (original Phase 6) follow v0.1 unchanged, built on checkpoints + bundles.

### Revised v0.1 Definition of Done

1. Install the server with one command; create the admin through the setup URL; no third-party accounts.
2. Create a workspace (empty or from a Git URL) and work fully in the browser: IDE, terminal, git, Node/PHP, Docker Compose.
3. Pair a laptop; clone a follower replica that stays current within seconds.
4. Take the workspace local, work offline, reconnect; history and working tree reach the server.
5. Kill the laptop while it holds the lease; take over from a browser; lose at most the last checkpoint interval.
6. Destroy the server; rebuild it from backup **or** from a replica.
7. In every scenario of §10, no acknowledged work is lost and no unacknowledged work disappears without a quarantine entry.

## 13. Product decisions (locked)

These were decided on 2026-10-04 and are binding for v0.1. Changing one is a design change, and the change must be reflected in the sections listed.

| # | Question | Decision | Reflected in |
|---|----------|----------|--------------|
| Q1 | Stop server processes when a device takes the workspace? | **Yes.** Development processes that can change the workspace stop on handoff to a device. Persistent services such as databases keep running. No per-workspace override in v0.1. | §4.3 |
| Q2 | Take the workspace automatically when a replica is edited and the server is idle? | **No.** Ownership changes only on an explicit action: `armageddon work local`, `armageddon work remote`, or the UI prompt *"Workspace is currently owned by Server. Take ownership?"* An idle-based policy may come after v0.1, once there is telemetry and more safety mechanisms. | §3.2, §3.3, F4 |
| Q3 | Keep `.env*` by default? | **Yes, with a prominent security notice.** Configurable with `sync.include_env`, plus a per-workspace server-side override. | §6.6 |
| Q4 | SSH endpoint in v0.1? | **Yes**, conditional on P8 passing. It gives Neovim, Vim, tmux, VS Code Remote-SSH and JetBrains access without per-editor integrations. | §2.3, P8 |
| Q5 | Multiple users in v0.1? | **Yes: a multi-user foundation with simple features.** Admin invites, workspace membership with `owner`/`member` roles. No teams, organizations, custom RBAC, SSO or billing. | §7.1, §7.4, §8.2 |
| Q6 | Checkpoint retention? | **All checkpoints: 24 h. Hourly: 7 d. Daily: 30 d. Checkpoints referenced by a snapshot or quarantine: kept permanently. Quarantines: kept until explicitly cleared.** Checkpoints come from debounced capture events, never from individual filesystem events. | §6.3, §6.7 |

Also changed in this revision:
- **The privileged helper's security boundary is explicit (§2.5):**
  - typed allowlisted API with no arbitrary root execution;
  - one Unix user per workspace;
  - all Git on workspace-writable repos runs as the workspace user;
  - Compose validation, and no Docker socket in workspaces.
- **Git pushes take a fencing lock (§4.2),** so a lease change cannot interleave with an in-flight `receive-pack`.
