# Armageddon v0.1: post-MVP implementation plan (draft)

Status: **Draft for review (2026-10-05).** This plan covers the six items left after the MVP merged (PR #3):

1. The P6 privilege-boundary prototype.
2. The M3.1 split into a root helper and an unprivileged server.
3. M7, local write mode.
4. M5, install and operations.
5. M4, remote IDE access (code-server and SSH).
6. The P2 round-trip prototype on macOS.

It refines [`v0.1-implementation-plan.md`](v0.1-implementation-plan.md) and keeps that plan's issue IDs (M3.1, M7.x, M5.x, M4.x), so the two can be read side by side. [`v0.1-architecture.md`](v0.1-architecture.md) remains the contract.

| # | Item | Phase | Why it sits there |
|---|------|-------|-------------------|
| 1 | P6 privilege boundary | 1 | Gates M3.1. The rule stands: no production change on an assumption that a prototype is meant to test |
| 6 | P2 on macOS | 1 | Moved forward from last place. It costs about half a day, and **no Mac is needed**: the existing `macos-latest` CI runner uses case-insensitive APFS. Its result decides how macOS replicas apply checkpoints, and macOS laptops are the main writers in M7 |
| 2 | M3.1 helper split | 2 | Every later phase spawns processes: the M7 handoff stops dev processes, the M5 systemd units need two services, and M4 starts code-server and SSH sessions. Doing the split first means those features are built once, against the final API |
| 3 | M7 local write mode | 3 | The core product promise. It needs the session registry and the helper's `SignalWorkspace` |
| 4 | M5 install and ops | 4 | Needs the two-process layout from Phase 2. Can start in parallel with Phase 3 |
| 5 | M4 remote IDE | 5 | Plugs new session kinds into the registry from Phase 3, and code-server is shipped by the release manifest from Phase 4 |

The one change from the order discussed earlier is that P2 on macOS moves from last to Phase 1. P8 (the SSH endpoint spike) also runs in Phase 1, in parallel; it gates only M4.4.

## 1. Baseline: what the MVP does today

These facts about the merged MVP shape the plan.

| Area | MVP behaviour | Changed in |
|------|---------------|------------|
| Privileges | The server runs as **root**. `internal/sysuser` creates `ws-<id>` with `useradd` and drops to it with `SysProcAttr.Credential` for every workspace process and Git command | Phase 2 |
| Seat capture | The seat shadow runs as `ws-<id>`. The server then moves the objects into `checkpoints.git` in-process, as root | Phase 2 |
| Session kinds | The browser terminal is the only kind. It is refused unless the server holds the lease | Phase 3, Phase 5 |
| Lease | A row exists and is checked on device pushes and commits, but it is **always held by the server**. No acquire, release or heartbeat API exists | Phase 3 |
| Agent | `armageddon follow` is a foreground long-poll loop per replica. It quarantines dirty edits when a checkpoint arrives, and it has no watcher | Phase 3 |
| Device key | A 0600 file. There is no Keychain or Secret Service integration | Phase 3 (optional) |
| Install | `server init` and `server run --listen … [--tls-cert/--tls-key]`. No installer, ACME, update or backup | Phase 4 |
| Hooks | A hook binary inside each workspace's hooks directory, passed as `core.hooksPath` | Phase 2 (socket path) |

## 2. Phase 1: Validate (≈1 week)

**Goal:** answer the open questions before any production code depends on them. Each prototype lives in `prototypes/Pn-*` and ends with a one-page write-up in `docs/design/prototypes/`, in the same format as Phase 0.

### 1.1 P6: the privilege boundary (3 days, blocking for Phase 2)

Build `prototypes/p6-privilege-boundary`: a throwaway helper and server pair that implements the contract §2.5 API exactly.

- **Helper:** runs as root. It listens on a 0600 unix socket owned by the `armageddon` user, checks the peer with `SO_PEERCRED`, and decodes a closed set of typed requests. PTYs and stdio pass as file descriptors (`SCM_RIGHTS`).
- **Server:** runs as `armageddon` and uses only the helper to create users, prepare directories and spawn processes.

**Escape matrix:** from a shell running as `ws-A`, each attempt below must fail.

| # | Attempt | Expected |
|---|---------|----------|
| E1 | Read `armageddon.db`, `keys/`, `checkpoints.git` | EACCES |
| E2 | Read or write `ws-B`'s `repo.git`, `tree/`, `home/` | EACCES |
| E3 | Signal the server, the helper or `ws-B`'s processes | EPERM |
| E4 | Connect to the helper socket | refused (file mode), and `SO_PEERCRED` rejects it if the mode is loosened |
| E5 | Plant `core.hooksPath`, `core.fsmonitor`, a filter driver, `core.sshCommand` or `diff.external` in `repo.git/config`, then trigger a push, a fetch, a seat capture and an `fsck` | Each runs only as `ws-A`; nothing runs as `armageddon` or root |
| E6 | Replace a workspace directory with a symlink to `/etc` before `PrepareWorkspaceDirs` runs | refused by `openat2(RESOLVE_BENEATH \| RESOLVE_NO_SYMLINKS)` |
| E7 | Reach the Docker socket | not present in the workspace's view |
| E8 | Submit a Compose file with `privileged`, host mounts or a Docker-socket mount | rejected (only the parser is prototyped; Compose itself is a later phase) |
| E9 | Escape the cgroup (fork bomb, memory hog) | the limits hold; the server and helper stay responsive |

**Also measured:**
- PTY, Git smart HTTP and seat capture all work through the helper.
- The cost of spawning through the helper, compared with the MVP's direct `setuid`: per Git request and per capture.
- A fuzz test of the request decoder, plus code review, shows there is no path that runs a caller-chosen program as root.
- **Docker variant:** helper and server in one container under different users, with per-workspace users created inside the container.
- **Fallbacks:** behaviour when cgroup v2 delegation or `openat2` (Linux 5.6+) is missing. Decide whether to refuse or degrade with a doctor warning.

**Pass criteria:** contract §11, P6 row. **Output:** `P6-privilege-boundary.md` and any proposed contract changes, numbered from ⟨P-15⟩.

### 1.2 P2 on macOS (½ day, blocking for Phase 3)

- Run `prototypes/p2-roundtrip` on the `macos-latest` runner (case-insensitive APFS). Use a smaller budget per PR and the full 10,000 sequences in a manual or nightly workflow.
- **Cross-platform check:** capture on the Linux job, upload the pack as a workflow artifact, apply it on the macOS job, then do the reverse.
- **Focus cases:** case-only renames, two names that differ only in case, NFC and NFD names, the executable bit, symlinks.
- **Expected outcome (contract §11):** collisions are detected and reported, and nothing is corrupted. Fixes go to both `prototypes/internal/gitshadow` and `internal/treesync/gitshadow`.

**Output:** an addendum to `P2-roundtrip.md`, plus a `macos-p2` CI job that keeps a small budget running on every PR.

### 1.3 P8: SSH endpoint spike (2 days, parallel, gates M4.4 only)

- Build an embedded SSH server (gliderlabs/ssh) that authenticates with the device Ed25519 keys and maps `ws-<slug>@server` to a server-seat shell.
- Check that VS Code Remote-SSH connects, installs its server, opens a folder and forwards a port; that JetBrains Gateway connects; and that SFTP works.

If it fails, M4.4 falls back to documenting a system `sshd` with a forced command, as recorded in the implementation plan's risk register.

### Gate G1

- P6 passes, or the contract is amended and the amendment approved.
- P2-macOS behaviour is documented and its CI job is green.
- P8 has a verdict. It may arrive later; it blocks only M4.4.

## 3. Phase 2: Privilege split, M3.1 (≈1.5 weeks)

**Goal:** the server runs as the unprivileged `armageddon` user, and every privileged action goes through `armageddon helper` and its allowlisted API.

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 2.1 | `armageddon helper` subcommand: socket setup, `SO_PEERCRED` check against the configured server uid, length-prefixed typed messages, a closed operation enum, fd passing | The decoder fuzz test is in CI. Unknown operations and extra fields are rejected. There is no `exec` of a caller-supplied path as root (enforced by review and a unit test that inspects the operation table) |
| 2.2 | Operations: `CreateWorkspaceUser`, `DeleteWorkspaceUser`, `PrepareWorkspaceDirs` (`openat2`), `SpawnInWorkspace` (kinds `pty-shell`, `git-service`, `runtime-command`; `code-server` and `ssh-session` reserved for Phase 5), `SignalWorkspace`, `SetWorkspaceLimits` (cgroup v2 under one `armageddon.slice`) | Each operation has a test for its validation failures. `SignalWorkspace` cannot reach a process outside the workspace cgroup |
| 2.3 | Replace `internal/sysuser` with a `helper.Client` interface that has two implementations: the socket client, and an in-process **dev** implementation that runs everything as the current user, for non-root development and unit tests | Same interface. Server code has no `syscall.Credential` and no `os/exec` call against `repo.git` or `tree/` outside the helper client (enforced by a `go vet`-style test that scans the package) |
| 2.4 | Checkpoint transport inside the server: the seat shadow runs `pack-objects` as `ws-<id>` through `git-service`, and the server runs `index-pack --fix-thin` on `checkpoints.git` as `armageddon`. Objects cross only as a pack stream (contract §2.5, last bullet) | The E5 escape tests pass: a poisoned seat `config` never runs as `armageddon` |
| 2.5 | Hooks talk to the authority over `/run/armageddon/<ws-id>.sock` (P-14). That socket accepts only its own workspace's uid (`SO_PEERCRED`) | A hook running as `ws-A` cannot write to `ws-B`'s socket |
| 2.6 | Terminal PTYs are opened by the helper and passed back as fds. The PTY is owned by `ws-<id>` | The UI terminal test passes unchanged |
| 2.7 | Upgrade path for MVP data directories (root-owned): the server checks ownership at startup and asks the helper to fix it. This is the only operation allowed to re-chown an existing tree, and it is limited to the workspace root | An MVP data directory starts under the new layout with no manual steps |
| 2.8 | Integration tests: the P6 escape matrix E1–E6 and E9 move to `test/integration/` and run on the CI runner under `sudo` | Green in CI |
| 2.9 | `mvp.sh` runs with the server as `armageddon` and the helper as root (two processes) | All 35 acceptance checks pass, and the UI test passes |

**Demo:** the MVP acceptance test passes unchanged, but `ps` shows only the helper running as root, and the escape suite is green.

## 4. Phase 3: Local write mode, M7 (≈3 weeks)

**Goal:** `armageddon work local` moves the writer to a laptop, `armageddon work remote` moves it back, and every failure path ends with the work in the current checkpoint or in quarantine. The phase also takes the pieces of M6 that M7 cannot work without.

### 3a. Agent groundwork (≈3 days)

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 3a.1 | `armageddon agent run`: one long-running process per user that manages all replicas, replacing one `follow` process per replica. `follow` becomes a thin client that registers a replica and tails its status. Ships a launchd plist and a `systemd --user` unit (`armageddon agent install`) | Survives restart and sleep or wake; one replica's error doesn't stop the others |
| 3a.2 | Watcher (fsnotify; FSEvents on macOS) feeding a debounced capture, with a periodic full-capture backstop. ⟨P-12⟩ scoped capture stays off | DIRTY is reported within 2 s (M6.7); the watcher falls back to full capture on overflow |
| 3a.3 | Agent ↔ server event channel: extend the existing long poll on `…/current` to carry lease events (`flush_and_release`, `granted`, `lease.forced`). WebSocket stays a later option | A lease event reaches the agent within 1 s |

### 3b. Lease protocol (≈4 days)

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 3b.1 | Authority commands `AcquireLease`, `ReleaseLease`, `Heartbeat` with conditional SQL and the fence taken as a writer (contract §4.1, §4.2). Replies carry `(holder, epoch, current)` (P-7, P-9). Rejections echo the attempted epoch (P-8) | Unit tests over every §3.2 transition, including the forbidden ones |
| 3b.2 | **Session registry** on the server: every interactive session (terminal now; code-server and SSH in Phase 5) registers with its workspace. On a lease change the server shows a banner and closes all sessions within 2 s (M4.6) | Simulated transfer closes two open terminals with a banner |
| 3b.3 | Server-seat handoff: flush (capture and commit), refuse when a Git operation is in progress (contract §5.6, F11), close sessions, then stop dev processes with `SignalWorkspace(all)` (Q1). With no Compose yet, "persistent services" is an empty set; Phase 4/M8 adds the exclusion | `work local` with a running dev server: the process stops and nothing is left writing to `tree/` |
| 3b.4 | Server worktree as a follower: apply each committed checkpoint as `ws-<id>` through the helper, with an apply journal. Server drift is quarantined as `source=server` (F14) | Edit `tree/` behind the lease's back: the next apply quarantines the edit and reports it |
| 3b.5 | CLI: `armageddon work local` and `work remote [--restart]`. The UI shows a holder banner and a "Work on server" button | The lease holder is visible everywhere: UI, `armageddon status` and the workspace API |

### 3c. Device writer loop (≈4 days)

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 3c.1 | Writer capture → thin pack upload (`POST …/checkpoints/pack`, reusing the P-1 transport) → `CommitCheckpoint(epoch, parent, oid)`. A pending queue on disk; retries are idempotent | Lost acks and duplicated requests never create a double commit (the seq is unchanged on retry) |
| 3c.2 | Ref push under the lease: watch `.git/refs` and `packed-refs`, then `push --atomic --prune` with `X-Armageddon-Epoch` through `http.extraHeader` per invocation. The MVP endpoint already enforces the device lease | A branch delete or force push from the device lands as a trash ref on the server |
| 3c.3 | Acquire with local edits: fast-forward when the server hasn't moved since the replica's last apply; otherwise quarantine first, then write from current (contract §3.3) | Both branches covered by tests |
| 3c.4 | Heartbeats; STALE in the UI; writer resync (P-9); missed-grant recovery (P-7) | The P4 liveness scenarios pass against the real server |

### 3d. Failure paths (≈4 days)

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 3d.1 | Forced takeover: in the UI with password re-auth, and in the CLI with `work remote --force`. Revoking a device is an immediate takeover | F2: the laptop dies holding the lease, a browser takes over, and the work continues from the last checkpoint |
| 3d.2 | Old holder returns: its writes are rejected with `lease_lost`, and its unacknowledged tail goes to `refs/quarantine/<device>/<ts>` | F2 follow-up: the tail is in quarantine and `quarantine diff` shows it |
| 3d.3 | Offline writing: the local checkpoint queue is committed in order on reconnect; if the lease was taken meanwhile, the whole queue is quarantined | F3: 1 h offline with 500 checkpoints reconciles in order |
| 3d.4 | Quarantine CLI: `list`, `diff`, `apply` (3-way merge, conflict markers), `export`, `drop`; a per-device quota; nothing is evicted automatically (Q6) | `apply` with overlapping edits produces conflict markers |

### 3e. Conformance and acceptance (≈3 days)

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 3e.1 | Port the P4 scenario generator to drive the real server and two agents (processes on one runner), with fault injection: kill -9 at commit and handoff steps, dropped and delayed responses through a proxy | Nightly: thousands of runs with no invariant violation. Per PR: a small budget |
| 3e.2 | `test/e2e/write.sh`: the north-star scenario with a laptop in local write mode, plus F2, F3, F4 and F18 | Green in CI |

**Alpha 2 exit test:** a laptop writes locally, dies mid-edit, and another machine takes over, losing at most one checkpoint interval. When the laptop returns, its tail is in quarantine.

**Optional within the phase:** device keys in Keychain or Secret Service (M6.1). This is a hardening step that doesn't block anything here; the 0600 key file stays as the fallback.

## 5. Phase 4: Install and operations, M5 (≈2 weeks)

**Goal:** a fresh VPS goes from `curl | sh` to a working server with TLS in under 10 minutes, and can be updated, rolled back, backed up and restored.

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 4.1 | Release pipeline (GitHub Actions, triggered by a tag): linux and darwin builds for amd64 and arm64, `manifest.json` with sha256 sums, minisign signature, pinned code-server artefacts for Phase 5 | The manifest verifies with the published key; a tampered artefact is refused |
| 4.2 | `install.sh`: OS and architecture detection; requirements (kernel, RAM, disk, git ≥ 2.40, installing git if missing); the `armageddon` user; the versioned layout in `/opt/armageddon` (contract §9.2); systemd units for the helper (root, capability bounding set, no network) and the server (`User=armageddon`, `NoNewPrivileges`, `ProtectSystem=strict`) | Installs on Debian 12, Ubuntu 24.04 and Fedora 40. Tested in CI with systemd-enabled containers, plus a manual VPS run per release. Re-running is idempotent |
| 4.3 | `server init`: a domain with ACME (certmagic; HTTP-01 on port 80 and TLS-ALPN-01 on 443), or IP-only mode with a self-signed certificate and its fingerprint. `armageddon login` pins the fingerprint on first use, trust-on-first-use style, and shows it for comparison | ACME works against the Let's Encrypt staging CA. In IP-only mode, a changed certificate is refused by the CLI |
| 4.4 | `server update [--to v]` and `rollback`: verify, back up the DB with `VACUUM INTO`, switch the `current` symlink, migrate, health check for 60 s, roll back automatically on failure | An injected migration failure rolls back the binary and the DB |
| 4.5 | `server backup` and `restore`: quiesce each authority briefly, `VACUUM INTO`, a `git bundle` of `repo.git` and of the checkpoint refs per workspace, keys optional and encrypted with a passphrase | Backup → fresh VM → restore gives identical refs and current checkpoints; workspaces come back READY with the server holding the lease |
| 4.6 | `armageddon doctor` (server): disk, permissions, helper reachability, git version, cgroup and `openat2` support (from P6), a sample `fsck`, and a DB/ref reconcile report | Each check has a failing fixture that `doctor` flags with a remedy |
| 4.7 | Docker Compose deployment: one image, helper and server as different users, `/var/lib/armageddon` on a volume | `docker compose up`, then `mvp.sh` against the container, passes |
| 4.8 | `server uninstall [--purge]` | `--purge` requires a typed confirmation |

**Alpha 1 exit test:** on a fresh VPS, using only a browser and SSH, run north-star steps 1–12, then continue from a different browser in under 10 minutes.

## 6. Phase 5: Remote IDE access, M4.3–M4.6 (≈2 weeks)

**Goal:** a borrowed laptop with only a browser gets a full IDE, and a laptop with VS Code gets Remote-SSH, both on the server seat.

| ID | Issue | Acceptance criteria |
|----|-------|---------------------|
| 5.1 | code-server lifecycle: one instance per workspace, spawned as `ws-<id>` through `SpawnInWorkspace(code-server)` on a unix socket inside the workspace. Started on demand, stopped after 30 min idle. The pinned version comes from the Phase 4 manifest (or a `server components install code-server` command for source installs) | Starts in under 5 s; stops after the idle timeout |
| 5.2 | Authenticated reverse proxy at `/w/<slug>/ide/` with session cookie and CSRF rules, WebSocket upgrade, and code-server's own auth disabled because only the proxy reaches its socket | No unauthenticated path reaches code-server: an integration test probes every route without a session |
| 5.3 | Embedded SSH endpoint (**only if P8 passed**): device keys, `ws-<slug>@server`, exec, PTY, SFTP, and port forwarding limited to the workspace's loopback. `armageddon ssh-config` writes a `Host` block | VS Code Remote-SSH and Neovim over SSH work end to end. Forwarding to another workspace's port is refused |
| 5.4 | Optional Git-provider credentials (M2.8): a PAT or a generated SSH key, encrypted at rest with the server data key. Exposed to the seat through a credential helper and an `SSH_AUTH_SOCK` proxy (M4.5) | `git push origin` to GitHub works from the browser terminal; the secret is never written into the workspace or returned by the API |
| 5.5 | Both new session kinds register with the Phase 3 session registry | `work local` closes an open code-server tab and an SSH session within 2 s, with a banner |

**Demo:** from a borrowed browser, edit in code-server and push to GitHub from the terminal. From a laptop, connect VS Code over Remote-SSH, then run `work local` and watch both remote sessions close.

## 7. Cross-cutting rules

- **One PR per phase,** or per sub-phase for Phase 3 (3a–3b, 3c–3d, 3e), so that each review stays readable. Each PR updates the contract first when the implementation shows the design was wrong (implementation plan principle 6).
- **No failure path left for later.** Each issue's acceptance criteria include at least one failure case, as in the main plan.
- **CI grows each phase.**
  - Phase 1: `macos-p2`.
  - Phase 2: `integration` (sudo).
  - Phase 3: `e2e-write`, plus a nightly conformance run.
  - Phase 4: `install` (systemd containers) and `release`.
  - Phase 5: the IDE proxy probes.
- **The MVP keeps working at every step.** `mvp.sh` and `ui.mjs` stay green on every PR.

## 9. Risks

| Risk | Signal | Mitigation |
|------|--------|-----------|
| The P6 fd-passing PTY or cgroup delegation behaves differently across distributions or inside Docker | P6 Docker variant | Doctor checks; a documented degraded mode without cgroup limits (a warning, not a silent change) |
| macOS case folding turns out to need more than "detect and report" | Phase 1.2 | Refuse to create the conflicting replica, with a clear error; record it in the contract as a known limitation for v0.1 |
| The helper hop makes Git HTTP noticeably slower | P6 measurement | Keep a long-lived `git-service` spawner per workspace instead of one helper round trip per request |
| Local write mode reveals protocol gaps that the P4 model missed | 3e.1 conformance runs | The model and the real system share the scenario generator, so a gap found in one is replayed against the other |
| Scope creep in Phase 4 (more distributions, packages) | review | Three distributions in v0.1; `.deb`/`.rpm` and Alpine after v0.1 |
