# Armageddon v0.1 — Implementation Plan (draft)

Status: **Draft.** Implementation starts after gate G0 (below). The plan builds on [`v0.1-architecture.md`](v0.1-architecture.md), which is the contract. It already assumes the prototype findings in PR #2 (`docs/design/prototypes/`) are accepted. Where it depends on one of those still-*proposed* changes, it says so with ⟨P-n⟩, so a rejection shows exactly what moves.

## 2. Principles for the build

1. **Server first, browser first.** Alpha 1 (end of M5) is usable with only a browser: no agent, no local replicas. Everything after it adds to a product that already works.
2. **Every milestone ends in a demo against the north-star scenario** (original plan §2), shrunk to that milestone's scope.
3. **Invariants are tests.** I1–I8 from the contract become integration tests the moment the code they constrain exists. The P4 model becomes a *conformance test*: the same scenarios run against the real authority through its API (M7.8).
4. **One binary, one repository, small packages.** Packages follow contract sections, so a design change maps to one package.
5. **No feature lands without its failure path.** Every issue's acceptance criteria include at least one failure or recovery case.
6. **The contract changes first.** If implementation finds the design wrong, a PR to `v0.1-architecture.md` lands before or with the code.

## 3. Repository layout

This is a refinement of original plan §36.

```
armageddon/
├── cmd/armageddon/            single binary: server | helper | agent | CLI subcommands
├── internal/
│   ├── config/                versioned config + migration of config files
│   ├── store/                 repository interfaces (§8)
│   │   ├── sqlite/            v0.1 implementation (modernc.org/sqlite)

│   ├── authority/             per-workspace actor, lease, fence, checkpoint commit (§4)
│   ├── workspace/             lifecycle state machine (§3.1), layout, import
│   ├── gitsvc/                Git HTTP front end, hooks, trash refs (§5)
│   ├── treesync/              TreeSync interface (§6.8)
│   │   └── gitshadow/         v0.1 implementation (from prototypes/internal/gitshadow)
│   ├── seat/                  server seat: worktree, sessions, handoff behaviour (§2.2, §4.3)
│   ├── helper/                privileged helper: typed API server + client (§2.5)
│   ├── terminal/              PTY over WebSocket
│   ├── ide/                   code-server lifecycle
│   ├── sshd/                  embedded SSH endpoint (§2.3)
│   ├── agent/                 device agent: replicas, watcher, retry loop, journal
│   ├── api/                   REST handlers, WS event bus, auth middleware
│   ├── events/                event and audit log
│   ├── tlsedge/               certmagic / IP-only self-signed + fingerprint
│   └── doctor/                checks shared by server and agent
├── web/                       dashboard (Next.js static export, embedded)
├── migrations/{common,sqlite}/
├── deploy/                    install.sh, systemd units, Dockerfile, compose.yaml
├── test/
│   ├── integration/           real git, real SQLite, real helper (in a container)
│   ├── e2e/                   multi-machine scenarios (containers as "laptops")
│   └── disaster/              §10 F1–F18 as automated tests
└── prototypes/                Phase 0 (read-only reference; deleted at v0.1)
```

Two notes on the layout:

- **The web UI is a static export embedded in the binary.** That keeps the single-binary promise; there's no Node runtime on the server.
- **The code-server version is pinned** in the release manifest.

## 4. Milestones

The weeks assume 1–2 engineers working full time. The estimates are for planning, not commitments, and are revisited at each milestone demo.

```
G0 ──▶ M1 Foundations ──▶ M2 Identity ──▶ M3 Workspace core ──▶ M4 Server seat ──▶ M5 Install & ops
 (≈1w)    (1w)              (1.5w)           (2.5w)                (2w)               (1.5w)
                                                                                          │
                                                       ═══ Alpha 1: browser-only, server-first ═══
                                                                                          │
                                M6 Agent & follower replicas ──▶ M7 Local write mode ──▶ M8 Runtimes & Docker ──▶ M9 Hardening
                                   (2w)                            (2w)                    (2w)                     (1.5w)
                                                                       │
                                                  ═══ Alpha 2: north-star scenario ═══
```

**Total: about 16 weeks from G0 to v0.1.** That is longer than the original 12, for three reasons: the helper and per-workspace users, the SSH endpoint, and the agent protocol additions found by P4. M8 can run in parallel with M6 and M7 if there is a second engineer, which brings it to about 13–14 weeks.

Each issue below lists dependencies (`deps`) and acceptance criteria (AC). An issue is done when its AC pass in CI and the code has been reviewed.

## 6. Risk register (implementation phase)

| Risk | Signal | Mitigation |
|------|--------|-----------|
| Capture too slow on very large repos (200k+ files) | P1 200k numbers; M9.3 | Scoped capture ⟨P-12⟩ behind a flag; document the supported size; fall back to a longer debounce |
| macOS filesystem behaviour (case, NFD) breaks apply | G0.7 | Detect collisions and refuse with a clear error rather than corrupt; a macOS E2E job from M6 |
| The helper grows into a general root API | code review | Fixed operation enum; decoder fuzz test; any new operation needs a contract change |
| VS Code Remote-SSH incompatibilities with the embedded SSH server | G0.8 | Fall back to documenting a system `sshd` with a forced command (functionally equivalent, more setup) |
| Scope creep from runtimes and Docker | milestone demos | M8 is deliberately thin; networking and snapshots stay post-v0.1 |
| One-engineer bus factor | — | Contract plus prototypes plus conformance suites make the system re-derivable |
